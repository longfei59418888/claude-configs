# 任务分析与实施方案文档规则

当被要求**分析任务、给出任务执行方案 / 需求方案 / 实施计划**时，必须把分析结果沉淀为一份**可执行的实施文档**，落盘到 `tasks/` 目录，而不仅仅在对话里口头给出。

## 落盘位置与命名

- 根目录：`tasks/`
- 按日期分子目录：`tasks/YYYY-MM-DD/`（当天日期，如 `tasks/2026-06-16/`）
- 文件命名：`<需求简称>需求分析和代码开发方案文档.md`
  - 例：`tasks/2026-06-16/用户登录需求分析和代码开发方案文档.md`
  - `<需求简称>` 用能一眼看懂的中文短名（如「用户登录」「会员付费」「金币系统」）
- 同一天多个需求各自一份文档，放在同一日期目录下。

## 文档定位

这是一份**经过分析、可以直接执行落地的实施文档**，不是泛泛而谈的概述。读者（包括另一个开发者或 AI）应当能照着它直接动手开发。必须做到：

- 基于对**当前代码库的真实分析**（现有模块、基础设施、约定），而不是凭空假设。
- 方案要具体到**文件、模块、接口、表、字段、流程**级别，可直接执行。
- 关键决策要写明**为什么这样选**，以及取舍。

## 文档结构（建议章节，按需裁剪但不可空泛）

1. **需求背景与目标**：要解决什么问题，范围边界（做什么 / 不做什么）。
2. **现状分析**：当前代码库相关部分的现状（涉及的模块、基础设施、可复用能力、约束）。
3. **需求拆解**：把需求拆成明确的功能点 / 用户故事。
4. **技术方案设计**：
   - 数据模型 / 表设计（涉及 SQL 时遵循 `sql-migration` 规则）
   - 接口设计（路径、入参、出参、权限）
   - 核心流程 / 时序（必要时用流程描述或图）
   - 与现有架构的衔接点（复用哪些 service、guard、装饰器等）
   - 关键决策与取舍
5. **实施步骤（任务清单）**：按可执行顺序拆成有序步骤，每步说明产出物和涉及文件路径；步骤之间标明依赖。
6. **风险与注意事项**：并发、一致性、安全、幂等、兼容等需要特别处理的点。
7. **验收标准**：怎样算完成（功能、测试、边界）。

## 工作流程

1. 先**实际阅读相关代码**再写方案，不要跳过分析直接给模板。
2. 写完文档后，在对话中给出文档路径和方案要点摘要。
3. 涉及需要用户拍板的关键决策，在文档中明确标注「待确认」，并在对话里向用户提出。
4. 后续按文档「实施步骤」推进开发；方案有调整时同步更新该文档。
